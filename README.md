# auto-invoice

공급사(롯데온 등)에서 송장번호를 자동으로 조회해서, 샵마인에 일괄
반영할 수 있는 엑셀 파일을 만들어주는 도구.

## 동작 방식

`scripts/run_all.py` 하나로 아래 8단계가 전부 자동으로 돌아간다.

1. **샵마인을 [배송중] 탭으로 맞춘다.** 다른 탭을 보고 있으면 그 탭으로 옮기고,
   탭이 닫혀 있으면 **[주문관리 > 배송중]** 메뉴로 다시 연다 (`shopmine/tabs.py`)
2. **쇼핑몰이 전부 연결돼 있는지 확인한다.** 끊긴 곳이 있으면
   **[연결안된 쇼핑몰 연결재시도]** 를 눌러 다시 연결하고, 그래도 남으면
   아무것도 하지 않고 멈춘다 (`shopmine/connect.py`)
3. 샵마인 **[주문관리 > 배송중]** 탭에서 **[송장수정모드]** 를 켜고, 수집 결과
   필터로 택배사가 **경동택배** / **직접** 인 주문만 골라 그리드 헤더의
   [전체선택]으로 전부 체크한다 (`shopmine/upload.py`, `shopmine/grid.py`)
4. `Alt+X`로 **체크한 주문만** 엑셀로 내보낸다. 내보내기 전에 엑셀 양식이
   **송장 자동화** 인지 확인하고, 다른 양식이면 그것으로 바꾼다 (`shopmine/export.py`)
5. 그 엑셀을 읽어 상품URL 도메인으로 공급사 어댑터를 찾아 송장번호를 조회하고,
   **발송정보일괄등록(수정용)** 형식의 CSV를 만든다 (`orchestrator.py`).
   어댑터가 `prepare_batch`를 갖고 있으면 주문상세를 열기 전에 **주문내역
   목록을 한 번 훑어** 아직 안 나간 주문을 걸러낸다(현재 롯데온). 목록에
   없는 상태거나 주문한 지 오래된 건은 예전처럼 상세를 연다.
   공급사끼리는 동시에 조회한다 - 사이트는 서로 상관이 없는데 한 줄로 세우면
   전체 시간이 모든 사이트의 합이 된다. 같은 사이트 안에서는 예전처럼 한 건씩
   순서대로 본다. 동시 개수는 `AUTO_INVOICE_WORKERS`(기본 4)로 정한다
6. `Alt+U`로 **[발송정보일괄등록(수정용)]** 창을 열고 CSV 경로를 넣어
   **[일괄등록]** - 그리드의 `송장번호(수정용)` 컬럼이 채워진다
7. 그 컬럼이 **채워진 행만** 체크하고 **[송장번호수정]** 을 한 번 눌러
   쇼핑몰까지 반영한다 (`shopmine/upload.py`)
8. 결과 창에 오류가 없으면 체크를 풀고 **[송장수정모드 끄기]** 로 마무리한다.
   반대로 **반영한 건이 하나도 없으면**(조회 성공 0건, 중간에 멈춤 포함)
   3단계에서 걸어둔 체크와 송장수정모드를 **작업 전 상태로 되돌린다**

```
python scripts/run_all.py --limit 5 --max-apply 5
python scripts/run_all.py --stop-before-apply   # 일괄등록까지만, 마지막은 사람이
```

5단계까지만 하고 업로드는 직접 하고 싶으면 기존 `scripts/run.py`(또는
바탕화면 `송장자동화` 아이콘)를 그대로 쓰면 된다.

### 왜 탭부터 맞추나

3단계 이후의 조작은 전부 **지금 보고 있는 탭**으로 간다. [송장수정모드 켜기]
좌표도, `Alt+X`(엑셀파일생성) / `Alt+U`(발송정보일괄등록)도 마찬가지다. 사람이
신규주문 탭을 열어둔 채로 두면 엉뚱한 화면을 조작하게 되므로, 맨 처음에
탭부터 맞춘다.

샵마인의 탭 하나는 **MDI 자식 창 하나**이고 창 제목이 곧 탭 이름이다. 그래서
좌표로 탭 막대를 클릭하지 않고 `WM_MDIACTIVATE`를 MDICLIENT에 보내 활성화한다
(`shopmine/tabs.py`).

### 왜 쇼핑몰 연결부터 확인하나

7단계 **[송장번호수정]** 은 파일을 만드는 게 아니라 샵마인이 **실제로 쇼핑몰에
접속해서** 송장을 등록하는 동작이다. 연결이 끊긴 쇼핑몰의 주문은 그때 가서
실패하는데, 그 시점에는 이미 다른 주문들이 반영된 뒤라 다시 맞추기 번거롭다.
그래서 화면을 건드리기 전에 먼저 본다.

확인은 메뉴바 오른쪽 **[쇼핑몰연결(Y)] > [쇼핑몰연결창(W)]** 을 열어
**연결상태 필터를 '연결안됨'** 으로 걸고, 목록이 비어 있는지로 한다. 목록이
비어 있지 않으면 **[연결안된 쇼핑몰 연결재시도]** 를 한 번 누르고 다시 본다.
그래도 남아 있으면 멈춘다.

이 창의 제목이 하필 6~7단계에서 '지금 쇼핑몰에 접속 중'을 뜻하는 창과 같은
`쇼핑몰 연결`이라, 확인이 끝나면 **반드시 닫는다** (안 닫으면 뒷단계가 계속
연결 중인 줄 안다).

### 왜 택배사가 '경동택배 / 직접'인 주문만 고르나

이 두 값은 실제 택배사가 아니라 **"아직 진짜 송장이 없다"** 는 표시다. 샵마인도
이걸 알고 있어서, 송장수정모드를 켜면 `송장번호(수정용)` 컬럼을 현재 송장번호로
미리 채워두면서 **이 두 종류만 비워둔다.**

그래서 이 한 가지 성질이 두 곳에서 쓰인다.

- 3단계: 고쳐야 할 주문을 고르는 기준 (필터 두 번 + 전체선택)
- 7단계: 일괄등록이 **실제로 반영된 행**을 가려내는 근거. 조회에 실패해 CSV에
  없던 주문은 그 칸이 여전히 비어 있으므로, "채워진 행"만 체크하면 정확히
  반영 대상만 남는다

체크 상태는 필터를 바꿔도, 필터를 초기화해도 유지된다. 그래서 필터를 두 번
갈아 끼우며 두 그룹을 모두 체크한 뒤 초기화하면 둘 다 체크된 채로 남는다.

### 멈추는 조건 (3중 브레이크)

실제 주문 데이터를 건드리는 자동화라, 조금이라도 화면이 예상과 다르면
진행하지 않고 멈추는 쪽을 택했다.

1. **화면 검증** - 창이 안 뜨거나, 버튼이 다른 창에 가려졌거나, 마우스 커서가
   목표 좌표에 도달하지 못하면 클릭하지 않는다
2. **건수 상한** - 조회 성공 건수가 `--max-apply`(기본 100)를 넘으면 CSV만
   만들어두고 샵마인은 건드리지 않는다
3. **필터 검증** - 필터를 걸 때마다 샵마인이 표시하는 `"경동택배"(으)로 필터됨.`
   라벨을 읽어 확인한다. 필터가 안 걸린 채로 전체선택을 하면 목록 전체가
   체크되기 때문이다
4. **체크 건수 대조** - 화면에서 체크한 건수가 기대 건수보다 **많으면** 진행하지
   않는다 (필터가 잘못 걸렸다는 뜻). 적으면 채워진 건만 반영하고 경고를 남긴다.
   기대 건수는 CSV 줄 수가 아니라 내보내기 엑셀의 **행 수**로 센다 - 아래
   '한 주문번호가 여러 행인 주문' 참고
5. **확인 대화상자 건수 대조** - 마지막 `[송장번호수정]` 확인창이 말하는
   "선택한 N개"의 N이 기대와 다르면 **[아니요]** 를 눌러 아무것도 반영하지 않는다

5번이 가장 강력하다. 샵마인이 스스로 알려주는 숫자를 검산하는 방식이라,
중간에 필터가 잘못 걸리는 등의 사고가 나도 엉뚱한 건수가 반영되지 않는다.

### 반영한 게 없으면 작업 전으로 되돌린다

멈추는 쪽을 택한 대가로, 멈춘 자리에 3단계의 흔적이 남는다 - 송장수정모드가
켜져 있고 대상 주문이 전부 체크된 상태다. 그대로 두면 두 가지가 곤란하다.
사람이 샵마인을 열었을 때 영문 모를 체크가 잔뜩 걸려 있고, 그 체크가 남은 채로
다음 실행을 하면 [송장번호수정] 확인창의 건수가 어긋나 또 멈춘다.

그래서 **샵마인에 반영한 건이 하나도 없으면** 실행이 끝날 때 되돌린다
(`pipeline.restore_shopmine`). 조회 성공이 0건이든, 상한에 걸려 멈췄든,
예상 못 한 오류로 죽었든 똑같다.

- 남은 확인창/일괄등록 창을 닫고
- 필터를 풀고 (필터가 걸려 있으면 [전체선택]이 화면 밖 체크까지 못 지운다)
- 체크를 전부 해제하고
- **우리가 켠 경우에만** 송장수정모드를 끈다 (사람이 미리 켜두고 실행했으면
  켜둔 채로 두는 것이 '작업 전 상태'다)

되돌리지 않는 경우가 둘 있다. **한 건이라도 반영됐으면** 오류가 있었더라도
화면을 그대로 둔다 - 무엇이 반영됐는지 사람이 확인해야 한다. `--stop-before-apply`
로 돌렸을 때도 그대로 둔다 - 사람이 이어서 [송장번호수정]을 누를 참이라
체크와 송장수정모드가 남아 있어야 한다.

되돌리기는 뒷정리라서, 실패해도 실행 결과를 덮지 않는다. 무엇을 못 했는지만
마지막 요약에 한 줄로 남긴다.

### 한 주문번호가 여러 행인 주문

샵마인 일괄등록은 `고객주문번호`만 보고 행을 찾기 때문에, 한 주문번호가
그리드에 여러 행(상품별 행)으로 있으면 CSV 한 줄이 그 행을 **전부** 같은
송장번호로 채운다. 실제로 2026-08-28 실행에서 주문 하나가 두 행이었고 그중
한 행만 송장이 나왔는데, 그대로 올렸다면 아직 발송되지 않은 나머지 행에도
같은 송장이 들어갈 뻔했다 (위 4번 브레이크에 걸려 멈췄다).

그래서 CSV를 만들 때 규칙을 하나 둔다 (`shopmine/excel_io.py`의
`resolve_duplicate_orders`):

- 그 주문의 **모든 행이 같은 송장번호로 조회 성공** -> CSV 한 줄로 합쳐 올린다
- 하나라도 빠지거나 송장번호가 서로 다르면 -> 그 주문은 통째로 빼고 리포트의
  실패 목록에 남긴다 (사람이 샵마인에서 직접 처리)

### 사람이 직접 처리해야 하는 주문

자동으로 처리하지 못했거나 그냥 넘기면 안 되는 주문은 실행이 끝날 때 네
갈래로 나눠서 보여준다. 넷 다 **수령인 이름**을 같이 찍는다 - 마켓 주문번호
만으로는 샵마인에서 그 주문을 찾기 번거롭기 때문이다.

- **실패한 주문** — 조회를 시도했지만 오류가 났다 (로그인 막힘, 화면 구조가
  바뀜, 한 주문에 송장이 여러 개 등). 다시 실행하면 풀릴 수도 있다.
- **아직 지원하지 않는 사이트** — 상품URL의 도메인에 맞는 공급사 어댑터가
  아직 없다. 그 주문만 사람이 직접 조회하거나, 어댑터를 새로 만들면 된다
  (아래 '새 공급사 추가하기').
- **취소/품절로 보이는 주문** — 공급사 화면에 '취소' 또는 '품절' 표시가 있어
  송장이 나올 수 없는 주문이다. '아직 송장번호 미발급' 스킵과 반드시 구분해야
  한다 - 저쪽은 기다리면 풀리지만 이쪽은 아무리 기다려도 안 풀려서, 섞어두면
  같은 주문이 매 실행마다 조용히 스킵되며 영영 남는다.
- **주문일이 2일 이상 지난 주문** — 송장이 아직 없어 **그냥 넘긴 주문** 중
  주문상세에 적힌 주문일이 오늘과 이틀 이상 벌어진 건이다 (예: 주문상세
  8월 26일 / 오늘 8월 28일). 발송이 늦어지고 있다는 뜻이다. 성공 건은 이미
  나가는 중이라, 실패 건은 사유부터 풀어야 해서, 취소/품절과 미지원 사이트는
  기다린다고 나올 건이 아니라 뽑지 않는다 - 그래서 위 세 갈래와 겹치지
  않는다 (`report.is_stale_entry`, 기준 일수는 `order_date.STALE_DAYS`).

주문일은 각 어댑터가 **주문상세 화면을 떠나기 전에** 같이 읽어둔다
(`suppliers/base.py`의 `with_order_date`). 송장이 안 나온 주문일수록 며칠
됐는지가 중요해서, 조회가 예외로 끝나도(미발급/취소) 그 예외에 날짜를 실어
결과까지 넘긴다. 화면에서 아무 날짜나 줍지 않고 '주문일자/결제일' 같은 라벨
바로 뒤에 붙은 날짜만 인정하며, 못 찾으면 아무 표시도 하지 않는다
(`order_date.py`) - 멀쩡한 주문을 '늦어짐'으로 잘못 올리면 목록 전체를 못
믿게 되기 때문이다.

취소/품절 판정(`suppliers/base.py`의 `raise_if_cancelled`)은 **송장번호를 못
찾은 경우에만** 한다. 주문상태를 정확히 읽을 수 있는 공급사(옥션/GS샵/무신사)는
그 상태값만 보고, 화면 전체 텍스트밖에 없는 공급사는 '진행중' 상태 문구도 없을
때만 본다 - 그러지 않으면 멀쩡한 주문 화면의 '주문취소' 버튼 이름에 걸린다.

### 주문일이 2일 지난 주문에 1:1 문의를 남긴다 (`inquiry.py`)

위의 '주문일이 2일 이상 지난 주문'은 사람이 공급사 화면을 하나씩 열어
"○○○ 배송 언제 시작하나요?"를 남겨왔다. GUI의 **[✉ 문의]** 버튼(또는
`scripts/inquire.py`)이 그 일을 대신한다.

- **입력은 결과 엑셀이다.** 바탕화면의 가장 최근 `송장조회결과_*.xlsx` 의
  [주문일지연] 시트에서 '지난 일수'가 **`2일`** 인 줄만 고른다. 오늘 다시
  계산하지 않고 엑셀에 적힌 값을 그대로 쓴다 - 조회를 돌린 날의 판단이
  기준이다. 3일 이상은 남기지 않는다 (2일이던 날 이미 남겼다). 출고/도착
  예정이 적혀 있어도 2일이면 남긴다.
- **장부로 중복을 막는다.** 남긴 주문은 `logs/inquiries.json` 에 마켓
  주문번호로 적고, 다시 돌려도 그 주문은 넘긴다. 한 건 남길 때마다 바로
  적어서 도중에 멈춰도 남긴 건은 장부에 있다.
- **어댑터에 `post_inquiry`가 있는 사이트만** 남긴다 (지금은 롯데온). 나머지는
  '아직 지원하지 않음'으로 결과에 남겨 사람이 직접 하게 한다. 사이트별로
  브라우저 하나를 열어 한 건씩, 송장조회와 같은 요청 간격으로 남긴다.
- **롯데온 화면 순서** (2026-09-04 실측): 주문상세 [문의하기](`button.btnInquiry`)
  → 툴팁 [고객센터 1:1문의] → 새 탭 `customerOneTone?odNo=...` (주문정보가
  이 odNo로 미리 채워진다) → [문의유형 선택] → 모달 [배송] → 바로 뜨는
  '상세유형 선택' 모달 [배송일정] → 내용 → [문자/알림톡] 체크(기본 해제) →
  [등록하기] → `confirm("1대1 문의를 등록하시겠습니까?")` → `alert("문의가
  등록되었습니다 ...")` → 문의내역으로 이동. 확인/완료가 자바스크립트
  dialog라 로그인 때처럼 핸들러로 받는다. 완료 문구를 못 받으면 성공으로
  치지 않는다.
- **결과는 바탕화면 `문의결과_*.xlsx`** 로도 남긴다 (`save_result_excel`). 송장조회
  결과 엑셀과 같은 생김새이고, 정렬은 실패 → 미지원 사이트 넘김 → 남김 →
  이미 남긴 주문 순 - 앞의 둘이 사람이 직접 남겨야 하는 건이다.

### 기다리는 시간은 '시계'가 아니라 '화면'을 보고 정한다

주문 하나를 조회하는 데 걸리는 시간의 대부분은 통신이 아니라 **고정 대기**였다.
어댑터 15곳이 모두 로그인 화면인지 보기 전에 무조건 1.5초를 잤다 - 리다이렉트가
자리잡을 시간을 주려던 것인데, 로그인이 살아 있는 평소 실행에서는 그게 통째로
낭비다(실측: SSF샵 주문 하나 1.87초 중 1.50초).

2026-08-31에 세션 없는 브라우저로 15곳 주문상세를 열어 재보니, **12곳은 서버가
302로 넘겨서 goto가 끝난 순간 이미 로그인 주소**였다. 자바스크립트로 넘기는
곳(무신사·CJ온스타일·NS홈쇼핑)만 뒤늦게 바뀐다. 그래서 판정을 이렇게 바꿨다
(`suppliers/common.py`의 `looks_like_login_page`).

- 기본은 **기다리지 않는다**. 지금 주소만 보고 판정한다
- 자바스크립트로 넘기는 사이트만 `settle_ms`를 줘서 그동안 주소를 지켜본다
  (바뀌는 순간 바로 끝낸다 - 끝까지 자지 않는다)
- 로그인 대기 루프의 '한 번 쉬기'는 판정 함수가 겸하던 것을 루프로 옮겼다

대신 그 고정 대기가 **화면이 그려질 시간**까지 겸하던 사이트가 있었다. 자바스크립트로
주문상세를 그리는 롯데온·지마켓·현대몰·네이버페이가 그렇고, 대기를 없애자 다 그려지기
전에 읽어서 '아직 미발급'으로 잘못 넘겼다. 그래서 **무엇을 기다리는지 명시**하도록
바꿨다(`common.wait_for_text`) - 화면에 그 주문의 주문번호(네이버페이는 [배송조회]
버튼)가 나타나면 다 그려진 것이다. 고정 1.5초보다 빠르면서(실측 0.3~0.7초) 느린
날에는 더 오래 기다려 준다.

실측(주문 22건, 같은 주문으로 전후 비교): **한 건당 평균 2.6초 -> 1.8초**.
사이트별로는 SSF샵 1.95->0.39초, 패션플러스 1.89->0.49초, GSSHOP 2.17->0.66초,
롯데온 2.05->1.29초다.

그때 못 훑은 다섯 곳(AK플라자·11번가·NS홈쇼핑·더현대는 1.5초, CJ온스타일은
2.5초)에 같은 처리를 마저 했다. 이쪽은 '화면이 그려질 시간'용 고정 대기라,
현대몰과 같은 방식으로 **그 주문의 주문번호가 화면에 뜰 때까지만** 기다린다
(`common.ORDER_RENDER_WAIT_MS`, 2초). 이미 그려져 있으면 0.01초에 지나간다.

표식으로 주문번호를 쓰는 데는 이유가 있다. '배송조회' 같은 글자는 상단 메뉴에도
있어서, 그걸 표식으로 삼으면 **아직 안 그려진 화면을 다 그려진 것으로 오인**해
멀쩡한 주문을 '아직 미발급'으로 넘길 수 있다. 주문번호는 그 주문의 상세가
실제로 그려졌을 때만 나온다. 끝내 안 보이면 2초를 채우고 넘어가는데, 예전
1.5초보다 0.5초 손해지만 덜 그려진 화면을 읽는 쪽이 훨씬 비싸다.

CJ온스타일은 그 2.5초가 '비로그인이면 홈으로 조용히 넘어간다'를 기다리는
역할까지 겸하고 있었다. 주문번호가 보이면 **로그인돼 있다와 다 그려졌다가 한
번에 확인**되므로(밀려나는 홈에는 그 번호가 없다) 거기서 끝내고, 안 보일 때만
예전처럼 주소로 판정한다(`_wait_until_order_detail`).

### 모달이 뜨기를 기다리는 것도 화면을 보고 정한다

위의 정리에서 '주문상세가 그려지기'까지는 화면을 보게 바꿨지만, **배송조회
버튼을 누른 뒤**는 그대로 고정 대기가 남아 있었다(롯데온·지마켓 1.5초,
롯데아이몰 1초). 실측해보니 누르고 나서 송장번호가 뜨기까지는 0.06~0.17초라,
그 차이가 주문마다 그대로 버려지고 있었다.

`common.wait_for_match`로 바꿨다 - 어댑터가 이미 갖고 있는 **송장번호 정규식**을
그대로 넘겨서, 그게 화면에 걸리는 순간 끝낸다. 읽을 곳이 사이트마다 달라서
(지마켓은 모달이 별도 iframe, 롯데아이몰은 팝업 창) '어디서 읽을지'는 함수로
넘긴다. 상한은 예전 고정 대기와 같은 값이라, 끝내 안 뜨는 화면에서도 예전보다
느려지지 않는다.

실측(같은 주문으로 이전 커밋 코드와 번갈아 A/B, 결과값은 양쪽 모두 동일):
**롯데온 한 건당 2.78초 -> 1.28초**, 지마켓 2.10초 -> 1.10초.

주의: 이 폴링에서 쉬는 것은 반드시 `page.wait_for_timeout`이어야 한다.
`time.sleep`으로 쉬면 Playwright 동기 API의 진행 자체가 멈춰서 기다리는 동안
화면이 그려지지 않는다(그렇게 만든 비교 코드에서는 같은 주문 4건이 전부
'미발급'으로 나왔다).

### 롯데온 주문목록도 카드가 늘어나는 것을 보고 넘긴다

`prepare_batch`(주문내역 목록 훑기)에도 같은 고정 대기가 있었다 - 목록 렌더에
8초, [더보기]를 누를 때마다 2.5초. 실측하니 첫 렌더는 1.47초, [더보기]는 14번을
눌러 합계 12.4초(고정값으로는 35초)였다. 카드(`.orderGroupWrap`) 수가 늘어나는
것을 보고 넘어가도록 바꿨고, 눌러도 안 늘면 목록의 끝으로 보고 멈춘다.

실측: **목록 훑기 39.9초 -> 12.9초** (찾아낸 주문 수는 70/70으로 동일).

롯데온은 매번 조회하는 주문의 절반쯤을 차지해서 전체 실행 시간을 사실상
혼자 정한다(실측 158건 중 73건). 위 두 가지를 합치면 그 사이트에 드는 시간이
약 260초에서 180초로 줄어든다.

### 랜덤 대기는 '추가로 자는 시간'이 아니라 '요청 사이 간격'이다

주문 사이의 랜덤 대기(`AUTO_INVOICE_DELAY_MIN`/`MAX`, 기본 1.5~4초)는 **다음
요청과 간격을 두려고** 넣는 것이다. 예전에는 성공/실패한 주문 '뒤에' 이 시간을
통째로 자서 실제 요청 간격이 '조회 시간 + 대기'(평균 4초쯤)로 설정값보다 늘
길었고, 반대로 요청을 보내고도 미발급이라 스킵한 주문 뒤에는 간격이 아예
없었다. 2026-09-01부터는 '요청을 시작한 시각 + 랜덤 간격' 전에는 다음 요청을
시작하지 않는 방식이다 - 조회에 걸린 시간이 간격에 포함되고, 요청을 보낸
주문이면 결과가 무엇이든 같은 간격이 지켜진다. 롯데온이 주문내역 목록만으로
답한 주문(요청 없음)은 간격을 세우지 않고, 대기가 요청 '앞'에 붙으므로
마지막 주문 뒤에는 자연히 쉬지 않는다.

덧붙여, 조회 시간의 대부분은 여전히 이 간격이다(조회 자체는 0.4~1.3초인데
간격이 평균 2.75초). 더 빠르게 하고 싶으면 어댑터가 아니라 `.env`의
`AUTO_INVOICE_DELAY_MIN`/`MAX`를 줄이는 것이 유일하게 의미 있는 손잡이다 -
다만 그만큼 봇 탐지에 걸릴 위험을 사는 것이라 기본값은 건드리지 않았다.

예외: 옥션/지마켓(이베이코리아)은 번들 크로미엄이라는 것 자체로 봇 확인
("로봇이 아닙니다", Cloudflare)에 걸린다 - 지마켓은 요청이 빠를 때, 옥션은
세션 갱신 리다이렉트에서 (2026-09-01 실측, 창을 띄워도 안 풀린다). 간격을
6~12초로 늘려 피하는 것도 해봤지만, 결국 두 사이트 모두 **우리가 직접 실행한
진짜 크롬(CDP, `WANTS_CDP_CHROME`)에서 조회**하는 것으로 정리했다 - 이
크롬에서는 봇 확인이 아예 안 뜨고, 떠도 저절로 풀려서 간격은 기본값을
그대로 쓴다. 실행 중 사이트당 크롬 창이 하나 뜨고, 탭 하나를 계속
재사용한다 (프로필: auth/chrome_profile_<사이트>).

옥션의 배송조회 화면(tracking.auction.co.kr)은 아직 발송 전인 주문에서
HTTP 500 오류로 떨어지므로, 주문상세 레이어에서 주문상태부터 읽고 발송된
주문만 배송조회를 연다. 봇 확인/차단으로 조회를 못 한 주문은 (어느
사이트든) 스킵이 아니라 **실패**로, 사유와 함께 기록된다.

## 샵마인 화면 자동화에 대해

처음에는 샵마인 상세정보/CS메모 창(`DataGridView`)을 Windows UI Automation으로
조회했다가 **샵마인이 여러 차례 크래시**했다. 그래서 한동안 화면은 전혀
건드리지 않고 엑셀 내보내기/업로드를 사람이 직접 하도록 두었다.

2026-08-27 다시 확인한 결과, 크래시가 나는 것은 **UI Automation으로 그리드를
읽을 때**였고, 창 열거(`EnumWindows`)·화면 캡처·마우스 클릭·키보드 입력은
앱을 죽이지 않았다. 그래서 지금은 **샵마인 화면(.NET) 쪽에는 접근성 API를 쓰지
않고** 마우스/키보드 조작으로만 자동화한다. `pywinauto`의 `uia` 백엔드는 이
프로젝트에서 쓰지 않는다.

딱 한 군데 예외가 `엑셀 파일 생성` 창의 **엑셀 양식 선택칸**이다. 이 창은
샵마인이 아니라 **별도 프로세스(`msedgewebview2.exe`)가 그리는 화면**이라
크래시와 무관하고, 지금 어떤 양식이 골라져 있는지는 색으로 알 수 없어 글자를
읽어야 한다. 그래서 이 창에 한해 MSAA(`oleacc`)로 **읽기만** 한다
(`shopmine/msaa.py`). 고르는 것은 여전히 클릭과 키 입력이다.

좌표 클릭에 의존하는 곳은 최소한으로 줄였다. 표준 Windows 대화상자(`#32770`)는
컨트롤 ID로, `발송정보일괄등록` 창은 컨트롤 핸들로 정확히 다룬다. 좌표가
필요한 곳은 WebView2로 그려진 `엑셀 파일 생성` 창의 버튼 두 개(하나는 색으로,
하나는 접근성 정보로 매번 위치를 찾는다)와 배송중 탭 툴바 3곳뿐이다. 자세한 함정과 방어는
`shopmine/winui.py` 상단 주석에 정리해두었다.

공급사 사이트(롯데온 등)는 이런 일괄 기능이 없어 계속 Playwright로 자동화한다
(Imperva 봇 차단이 있어 로그인된 브라우저 컨텍스트 안에서만 API 호출이 통과함을
확인했다).

## 1단계 — 공급사 어댑터 검증

```
python scripts/check_adapter.py "<공급사 주문상세 상품URL>"
```

어느 어댑터를 쓸지는 실제 실행과 같이 URL의 도메인으로 정하므로, 사이트마다
스크립트가 따로 있지 않다. 상품URL은 샵마인 발송대상 엑셀의 `상품URL` 값이나
`logs/run_*.json`에서 하나 가져다 쓰면 된다 - **지금 살아 있는 주문**으로
확인해야 실패했을 때 어댑터 문제인지 주문 만료인지 헷갈리지 않는다.

`.env`에 `LOTTEON_ID`/`LOTTEON_PW`를 넣어두면 로그인 세션이 없을 때 사람
개입 없이 자동으로 로그인한다(SSG·더현대·NS홈쇼핑·11번가·옥션·패션플러스·
롯데아이몰·AK플라자·무신사·현대몰·CJ온스타일·SSF샵·W컨셉·포스티·29CM·4910과 동일한 방식). GSSHOP만은 완전
무인이 아니다 - 아이디·비밀번호 입력과 제출까지는 자동이지만, 그 사이트의
reCAPTCHA가 자동화 브라우저에는 늘 사람 확인을 요구해서 뜬 창에서 '로봇이
아닙니다'를 한 번 통과시켜 줘야 한다(그 뒤는 자동). 현대몰과 CJ온스타일은
로그인하는 동안 크롬 창이 잠깐 떴다가 닫히는데, 두 사이트의 봇 확인(현대몰은
reCAPTCHA, CJ온스타일은 Cloudflare Turnstile)이 설치된 진짜 크롬에서만
통과되기 때문이다(사람이 타이핑하거나 체크박스를 누를 일은 없고, 조회는
평소처럼 창 없이 진행된다 - 자세한 내용은 `.env.example`의 `HMALL_PW`/
`CJONSTYLE_PW` 설명). `LOTTEON_PW`를 비워두면 예전처럼 브라우저 창이 뜨고,
직접 로그인하면 자동으로 감지해서 이어서 진행한다.

W컨셉도 현대몰·CJ온스타일과 같이 로그인하는 동안만 크롬 창이 떴다가 닫힌다
(reCAPTCHA Enterprise가 걸려 있어 번들 Chromium으로는 통과되지 않는다). 이
사이트는 봇 확인에 걸리면 단순히 실패로 끝나지 않고 **30분 간 로그인이
제한되므로**, 실패 사유를 받으면 그 자리에서 조회를 멈춰 한 번 실행에 로그인
시도가 최대 1회가 되게 해뒀다.

포스티는 창이 뜨지 않는다. 다만 로그인만은 화면을 거쳐야 하고(로그인 API를
직접 부르면 "잘못된 접근입니다"로 막힌다), **로그인 화면을 연 뒤 6초쯤 머문
다음에 제출해야** 통과한다 - 열자마자 제출하면 같은 이유로 거부당한다.
조회는 로그인 뒤 쿠키만 있으면 GraphQL 한 번으로 끝나서 페이지를 아예 열지
않는다(사이트 중 유일하게 조회에 브라우저 화면이 필요 없다).

무신사는 계정을 3개 쓰기 때문에 `MUSINSA_ID`/`MUSINSA_PW`,
`MUSINSA_ID2`/`MUSINSA_PW2`, `MUSINSA_ID3`/`MUSINSA_PW3`를 각각 넣는다.
최초 세팅은 `python scripts/musinsa_login_setup.py`를 한 번 돌리면 세 계정
세션이 한꺼번에 만들어진다(계정별 주문 URL을 하나씩 넘기면 조회까지 확인된다).

29CM는 무신사 통합계정 체계라 29CM 자체 이메일 로그인이 아니라 로그인 화면의
"무신사 통합계정" 버튼을 거쳐 로그인한다(어댑터가 알아서 한다 - 창도 뜨지
않는다). 계정은 `29CM_ID`/`29CM_PW`를 먼저 보고, 비어 있으면 같은 통합계정인
`MUSINSA_ID`/`MUSINSA_PW`를 그대로 쓴다. 조회는 주문목록 API 한 번으로 이번에
조회할 주문 전부를 통째로 읽어(목록 항목이 상세 응답과 같은 구조다) 주문이 몇
건이든 요청 하나로 끝나고, 요청을 안 보낸 주문에는 간격도 두지 않는다. 목록에
없는 주문(3개월보다 오래됨 등)만 상세 API로 하나씩 확인한다.

4910은 에이블리가 운영하는 남성 패션몰이라 백엔드가 에이블리 API다. 로그인만
이메일 로그인 화면을 창 없이 거치고(캡차 없음, `4910_ID`/`4910_PW`), 조회는
주문목록 API 한 번을 캐시해두고 발송된 주문만 배송조회 API를 하나씩 부른다 -
페이지를 아예 열지 않는다. 상품URL이 `/order/<주문번호>` 형태가 아니어도
주문목록에서 상품번호·주문옵션·수령인 이름 순으로 좁혀 맞는 주문을 찾아준다.
택배사는 어떤 표기로 오든(CJ/대한통운/롯데/DELIBOX) 샵마인이 아는 이름
(CJ대한통운/롯데택배/딜리박스)으로 맞춰 올린다.

로그인 세션은 `auth/<사이트>_state.json`에 저장되어 다음부터는 다시 로그인하지
않는다. 넘긴 주문의 송장번호가 나오면 성공이다(`--expect <송장번호>`로 값까지
맞는지 비교할 수 있다).

자동 로그인만 따로 검증하려면(저장된 세션을 무시하고 로그인부터 다시):

```
python scripts/check_adapter.py --fresh "<상품URL>"
```

성공했을 때만 새 세션을 저장한다 - 실패하면 멀쩡한 기존 세션을 건드리지 않고
마지막 화면을 `logs/`에 남긴다.

## 2단계 — 샵마인에서 발송대상 엑셀 받기

샵마인에서 **주문관리 > 발송대상 > 엑셀파일생성** 으로 엑셀(.xls)을 받는다.
아래 두 컬럼이 반드시 포함되어야 한다 (컬럼 순서는 무관):

- `마켓 주문번호`
- `상품URL`

**옥션 주문이 섞여 있으면 `수령인`과 `주문옵션` 컬럼도 반드시 포함해야 한다.**
옥션은 주문상세/배송조회가 전부 자바스크립트 팝업이라 상품URL에 주문번호가
들어가지 않고 목록 페이지 주소(`.../Close/OrderProcessList.aspx`)만 들어온다.
그래서 옥션 주문내역(**최근 1개월**)을 훑어서 **주문옵션이 맞는 후보를 고른 뒤
"받으시는 분"이 `수령인`과 같은 주문**으로 확정한다. 실제 주문내역을 받아보니
`RBK / 260 / 40,000원 / 1개` 같은 옵션이 5건 넘게 반복돼서, 옵션만으로는 절대
확정하지 않는다. (상품URL에 `?order_no=<주문번호>`가 들어있으면 목록을 훑지
않고 바로 조회한다.)

주문한 지 1개월이 넘은 건은 조회되지 않는다 — 더 옛날 것까지 보려면
`suppliers/auction.py`의 `LIST_PERIOD_DAYS`/`SEARCH_TERM_ONE_MONTH`를 조정한다.

(참고: 샵마인이 만드는 파일은 구버전 `.xls` 형식이라 `.xlsx`와 다르다.
이 도구는 `.xls`/`.xlsx` 둘 다 읽을 수 있다.)

## 3단계 — 실행

```
python scripts/run.py --input "C:\Users\admin\Desktop\실제로_내보낸_파일명.xls" --limit 3
```

`--input`에는 위에서 실제로 내보낸 파일의 진짜 경로를 넣는다 (아래는
예시일 뿐 실제 경로가 아니다 — 보통 바탕화면이나 다운로드 폴더에 저장됨).

- `--limit`으로 먼저 적은 수만 테스트해본다
- 처리 결과는 콘솔에 요약되고, `logs/run_*.json`에 상세 리포트가 남는다
- 같은 내용이 바탕화면 `송장조회결과_YYYYMMDD_HHMMSS.xlsx`로도 저장된다 —
  주문별 결과/송장번호/반영 여부를 사람이 바로 열어볼 수 있는 형태다
  (`result_excel.py`). 손이 필요한 건(실패 -> 미지원 사이트 -> 취소·품절)이
  위로 올라오고, [요약] 시트에 건수와 관련 파일 경로가 들어간다.
  주문일이 2일 이상 지난 건은 '주문일' 칸이 빨갛게 표시되고 목록에서도
  실패/취소·품절 다음으로 올라오며, 그 건만 모은 [주문일지연] 시트가
  따로 붙는다
- 성공한 건이 하나라도 있으면 바탕화면에 `송장자동화_YYYYMMDD.csv`
  (기본 경로, `--output`으로 변경 가능)가 생성된다 — 이게 샵마인에
  업로드할 파일이다

## 4단계 — 샵마인에 업로드

생성된 `송장자동화_YYYYMMDD.csv`를 열어 내용이 맞는지 한 번 확인한 뒤, 샵마인
**발송정보일괄등록(수정용)** 창에서 그 파일을 선택하고 **일괄등록**을
누른다. 업로드는 xlsx를 지원하지 않아(xls, csv만 지원) CSV로 만든다.
택배사를 별도로 지정하지 않아도, 생성된 파일에 이미 택배사 컬럼이
채워져 있다.

**처음 한 번은 꼭 1건으로만 테스트해서, 실제로 "맞는 주문"에 송장번호가
붙는지 샵마인 화면에서 직접 확인해주세요.** 식별 컬럼으로 "고객주문번호"
(값은 내보내기 파일의 "마켓 주문번호")를 쓰도록 만들었는데, 이게 샵마인
내부에서 기대하는 것과 정확히 같은 의미인지는 실제 업로드로 확인해야
합니다.

## 새 공급사 추가하기

1. `src/auto_invoice/suppliers/_template.py`를 `<공급사명>.py`로 복사
2. 필요하면 롯데온과 같은 방식으로 Network 탭 HAR 캡처를 떠서 실제 API를
   찾는다 (막히면 페이지를 직접 스크래핑하는 방식으로 대체)
3. `DOMAINS`, `SITE_KEY`, `get_tracking()`을 채운다
4. `src/auto_invoice/suppliers/registry.py`에 두 줄 추가:
   ```python
   from . import <공급사명>
   register(<공급사명>)
   ```

`orchestrator.py`는 건드릴 필요가 없다.

## 안전장치

- 샵마인에는 항상 사람이 검토한 엑셀 파일로만 반영된다 (화면 자동화 없음)
- 주문 하나가 실패해도 배치 전체가 멈추지 않는다 (건별 예외 처리)
- 반영 단계에서 멈추거나 예상 못 한 오류가 나도, 이미 끝낸 송장조회 결과는
  잃지 않는다. `run_full`은 조회 이후를 try/finally로 감싸 결과 엑셀을 항상
  남기고, 마지막 요약에 `송장조회는 끝냈습니다: ...`로 다시 실어준다
- 매 실행마다 `logs/run_*.json`에 성공/실패/스킵 요약을 남긴다. 고객
  개인정보(주소/전화번호 등)는 기록하지 않는다. 유일한 예외는 사람이 직접
  손봐야 하는 건(실패 / 미지원 사이트 / 취소·품절)의 **수령인 이름**으로,
  샵마인에서 그 주문을 찾으려면 필요해서 남긴다
- 공급사 사이트 요청 사이에 랜덤 대기(`AUTO_INVOICE_DELAY_MIN/MAX`)를
  넣어 과도한 트래픽으로 보이지 않게 한다. `--limit`으로 1회 처리량도
  제한할 것. 동시 조회는 **사이트별로 나눠서**만 한다 - 한 사이트에 요청을
  겹쳐 보내지 않으므로 사이트가 보는 요청 간격은 예전 그대로다
- 조회용 브라우저는 이미지/폰트/동영상을 받지 않는다(`browser.py`). 사람에게
  로그인을 넘길 때만 차단을 풀고 화면을 다시 불러온다 - 캡차가 이미지로 나오는
  사이트가 있다
- `auth/`, `logs/`, `.env`는 모두 gitignore 대상이다. 로그인 세션과
  자격증명, 실행 기록은 절대 커밋하지 않는다
